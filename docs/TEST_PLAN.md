# 테스트 계획 — 작은 원정대

## 1. 범위

| 영역 | 위험 | 대응 |
|---|---|---|
| 모집(가챠) | 공시 확률과 실제 확률 불일치, 천장 off-by-one, 재화만 빠지고 결과 미지급 | 경계값 TC + 통계 검정 + 확률 검증기 |
| 기획 데이터 | 확률 합계 오류, 오타 id, 순환 참조가 그대로 빌드에 포함 | DataValidator (CI + 빌드 훅) |
| 전투 | "가끔" 지는 버그를 재현할 수 없음 | 시드 결정적 시뮬레이터 + battle-replay |
| QA 도구 | 재현 도구가 게임이 만든 값(시드·명령줄)을 못 읽거나 다르게 읽어, 리포트의 시드로 재현이 안 됨 ([BUG-003](bug-reports/BUG-003-replay-seed-above-long-max-rejected.md)) | 도구 입력 경계값 TC(TOOL-xxx) + 게임이 찍은 명령줄을 그대로 넣는 회귀 TC + qa-tool 뮤테이션 |
| 턴제 전투 | 행동 순서 동점·사망 유닛 차례·쿨타임 off-by-one·상태이상 중첩 같은 경계 오류, 동시 전멸 오판, 보상 중복 지급, 사람이 고른 명령이라 재현 불가 | 규칙을 Core 주석에 기획서처럼 고정 + 경계값 TC(TURN-xxx) + 시드·명령 목록 리플레이(turn-replay) + 턴제 뮤테이션 |
| 턴제 전투 연출(2.5D) | 화면의 HP·쓰러짐·상태이상이 실제 전투 상태와 다름, 연출이 결과보다 앞서 보임, 배속·건너뛰기에 따라 결과가 달라짐, 연출 중 연타로 명령이 잘못 들어감 | 연출은 계산하지 않고 Core 로그만 재생 + 화면 상태를 엔진 밖 클래스(`TurnBattleDisplay`)로 분리해 300판 대조(TURN-025~027) + 실제 화면 대조·배속·연타 PlayMode 테스트(TURN-028~030) + 재생이 끝날 때마다 게임이 스스로 대조해 다르면 오류 로그 |
| 미니게임 | 판정 경계 부동소수 오차, 보상 중복 수령, 프레임에 따라 다른 결과 | 시간 주입 설계 + 경계값 TC + 리플레이 |
| 세이브 | 깨진/변조된 세이브로 크래시, 저장 후 결과가 달라짐 | 검증 후 거부 + 깨진 파일 보관 + 시드 저장 |
| UI | 화면과 규칙 연결 끊김, 리소스 누락 시 진행 불가 | PlayMode E2E + 기본 카드 대체 |
| 홈 로비 연출(2.5D) | 로비에 선 캐릭터가 실제 편성과 다름, 캐릭터 탭 같은 연출이 세이브·게임 난수를 건드림, 화면을 오갈 때 3D 무대·카메라가 남아 겹침 | 로비는 Core의 자동 편성을 받아 그리기만 함 + 탭 전후 세이브 직렬화 비교·무대 수 세기 PlayMode 테스트(LOBBY-001~004) |

범위 밖: 서버·결제·네트워크(이 게임은 오프라인), 본격적인 성능 측정(전투 화면 프레임 시간만 자동 플레이가 기록), 다국어.

## 2. TC 작성 기준

- 한 TC = 확인할 동작 하나. `TC_ID`는 `영역-번호`.
- **우선순위**: P0 = 재화·확률·진행이 막히는 문제 / P1 = 잘못된 결과지만 우회 가능 / P2 = 드문 입력·표시 문제.
- **유형**: 기능 · 경계값 · 예외 · 확률 · 회귀 · 탐색 · 호환성.
- 경계값은 "경계 바로 안 / 경계 / 바로 밖" 세 점을 본다 (예: 천장 89·90회, 보석 149·150, 판정 0.46·0.4599).
- **자동화**: 결정적으로 판정할 수 있으면 Y. 사람의 체감이 필요한 것(터치 지연, 레이아웃 미관)은 N.
- **실행환경**: `dotnet`(엔진 없이 + Unity EditMode에서도 실행) / `qa-tool`(도구 자체 테스트, dotnet에서만) / `unity-playmode` / `수동`.

## 3. 자동화 원칙

1. **규칙은 엔진 밖에서 테스트한다.** 게임 규칙은 `Core`(엔진 참조 없음)에 두고, UI 테스트는 "연결"만 본다.
2. **결정적으로 만든다.** 난수는 시드 PCG32, 시간은 외부에서 주입. 통계 테스트도 시드를 고정해 flaky 하지 않다.
3. **TC 번호로 잇는다.** 모든 자동화 테스트에 `[TC("...")]`. 리포트가 문서와 결과를 자동으로 대조한다.
4. **테스트를 테스트한다.** 뮤테이션 스모크로 대표 버그 40개(턴제 규칙 11개 · 턴제 화면 상태 5개 · 그림 리소스 2개 · qa-tool 2개 포함)를 넣어 테스트가 잡는지 확인한다.

## 4. 통계 테스트 기준

- 카이제곱 적합도 검정, 유의수준 0.001 (시드 고정이라 같은 코드면 항상 같은 p값).
- 천장 포함 실제 확률: 이론값 `p / (1 - (1-p)^N)` 과 공시값 비교. 시뮬레이션 관측값은 공시값 ± 4σ + 반올림 오차 이내.
- 확률 검증기는 배너당 100만 회(CI), 단위 테스트는 20~30만 회.

## 5. 결과 판정 (릴리스 기준)

- P0 TC 실패 0, 자동화 누락 0, 문서에 없는 TC 번호 0.
- 데이터 검사 Error 0.
- 확률 검증 전부 통과.
- 미실행(실행 환경 없음)이 있으면 "실행한 범위 통과"로만 표시하고 릴리스 판정은 보류.

## 6. CI 확장 (Unity 테스트)

지금은 Unity 라이선스가 필요 없는 부분만 GitHub Actions에서 돈다. Unity 테스트까지 CI에 올리려면:

1. Unity Personal 라이선스 파일을 저장소 시크릿 `UNITY_LICENSE`, `UNITY_EMAIL`, `UNITY_PASSWORD`로 등록
2. `game-ci/unity-test-runner`로 `testMode: all`, `projectPath: UnityProject` 실행
3. 결과 XML을 `qa report --results ...,unity-editmode=...,unity-playmode=...` 에 함께 넣기

## 7. 개발 단계별 테스트 계획

이 게임은 혼자 만든 작은 프로젝트라 실제로 단계를 나눠 개발하지 않았습니다. 아래는 **이 프로젝트를 팀 신작으로 진행한다면** QA가 단계마다 무엇을 하고, 무엇을 남기고, 언제 다음 단계로 넘길지 정리한 계획입니다. 서버·결제는 이 게임 범위 밖(1장)이므로, 서버가 생기는 단계에서는 범위를 다시 정합니다.

| 단계 | QA 범위 | 진입 기준 | 종료 기준 | 산출물 |
|---|---|---|---|---|
| 프로토타입 | 핵심 재미 확인 (모집 연출, 미니게임 손맛). 규칙이 자주 바뀌므로 수동 탐색 위주, 자동화는 최소 | 플레이 가능한 빌드 | 핵심 루프(모집→원정→미니게임)가 막힘 없이 한 바퀴 | 탐색 메모, 초기 위험 목록(1장 표) |
| 알파 | 시스템별 기능 검증. **기획 리뷰**로 질문·TC를 만들고, 규칙이 굳은 곳(확률·천장·재화)부터 자동화. 데이터 검사기를 빌드 전 훅에 연결 | 기능 명세 1차본, 개발 빌드가 매일 나옴 | P0 TC 작성 완료, 데이터 검사 Error 0, 빌드 스모크 CL 통과 | [기획 리뷰](spec-review/gacha.md), [TC](test-cases.csv), [빌드 스모크 CL](checklists/build-smoke.csv), 자동화 테스트, [버그 리포트](bug-reports/README.md) |
| CBT | 실제 사용자 흐름 전체. 회귀(지난 빌드에서 고친 버그 재발 여부)를 매 빌드, 확률 검증·추적 리포트를 CI에서. 사용자 제보는 시드·리플레이 문자열로 재현 | 콘텐츠 잠금(신규 시스템 추가 중단), P0 버그 0 | P0·P1 미해결 0, 릴리즈 CL 1회 전체 통과, 확률 검증 통과 | [릴리즈 CL](checklists/outgame-release.csv) 결과 시트, 테스트 결과 보고, 제보 재현 기록 |
| 출시 | 릴리스 후보 빌드의 최종 확인. 5장의 릴리스 기준 판정. 출시(비개발) 빌드에서 디버그 패널 제외 확인 | 릴리스 후보 빌드, 코드 동결 | 5장 기준 전부 충족, 릴리즈 CL 통과, 알려진 이슈 목록 승인 | 릴리스 판정 기록, 알려진 이슈 목록 |
| 라이브 업데이트 | 바뀐 곳 + 영향 범위 회귀. 배너 교체 같은 **데이터만 바뀌는 업데이트**도 데이터 검사·확률 검증·모집 CL을 다시 돎. 세이브 호환(이전 버전 세이브 읽기) 확인 | 업데이트 명세, 바뀐 데이터·코드 목록 | 바뀐 영역 CL 통과, 전체 자동화 통과, 세이브 호환 확인 | 업데이트별 영향 범위 표, 회귀 결과 |

### 단계와 상관없이 매번 하는 것

- **새 빌드를 받으면**: 빌드 스모크 CL (10~15분). 실패하면 그 빌드는 테스트를 멈추고 개발에 돌려보냄.
- **버그를 고치면**: 회귀 TC를 먼저 추가하고(예: BUG-001 → GACHA-015, BUG-002 → DATA-010, BUG-003 → TOOL-001~004), 뮤테이션 스모크 목록에도 같은 유형을 넣어 테스트가 그 버그를 잡는지 확인.
- **기획 데이터가 바뀌면**: `qa validate-data` + `qa gacha-verify`. 데이터만 바뀌어도 결함이 생길 수 있음 (BUG-002).

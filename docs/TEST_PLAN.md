# 테스트 계획 — 작은 원정대

## 1. 범위

| 영역 | 위험 | 대응 |
|---|---|---|
| 모집(가챠) | 공시 확률과 실제 확률 불일치, 천장 off-by-one, 재화만 빠지고 결과 미지급 | 경계값 TC + 통계 검정 + 확률 검증기 |
| 기획 데이터 | 확률 합계 오류, 오타 id, 순환 참조가 그대로 빌드에 포함 | DataValidator (CI + 빌드 훅) |
| 전투 | "가끔" 지는 버그를 재현할 수 없음 | 시드 결정적 시뮬레이터 + battle-replay |
| 미니게임 | 판정 경계 부동소수 오차, 보상 중복 수령, 프레임에 따라 다른 결과 | 시간 주입 설계 + 경계값 TC + 리플레이 |
| 세이브 | 깨진/변조된 세이브로 크래시, 저장 후 결과가 달라짐 | 검증 후 거부 + 깨진 파일 보관 + 시드 저장 |
| UI | 화면과 규칙 연결 끊김, 리소스 누락 시 진행 불가 | PlayMode E2E + 기본 카드 대체 |

범위 밖: 서버·결제·네트워크(이 게임은 오프라인), 성능 측정, 다국어.

## 2. TC 작성 기준

- 한 TC = 확인할 동작 하나. `TC_ID`는 `영역-번호`.
- **우선순위**: P0 = 재화·확률·진행이 막히는 문제 / P1 = 잘못된 결과지만 우회 가능 / P2 = 드문 입력·표시 문제.
- **유형**: 기능 · 경계값 · 예외 · 확률 · 회귀 · 탐색 · 호환성.
- 경계값은 "경계 바로 안 / 경계 / 바로 밖" 세 점을 본다 (예: 천장 89·90회, 보석 149·150, 판정 0.46·0.4599).
- **자동화**: 결정적으로 판정할 수 있으면 Y. 사람의 체감이 필요한 것(터치 지연, 레이아웃 미관)은 N.
- **실행환경**: `dotnet`(엔진 없이 + Unity EditMode에서도 실행) / `unity-playmode` / `수동`.

## 3. 자동화 원칙

1. **규칙은 엔진 밖에서 테스트한다.** 게임 규칙은 `Core`(엔진 참조 없음)에 두고, UI 테스트는 "연결"만 본다.
2. **결정적으로 만든다.** 난수는 시드 PCG32, 시간은 외부에서 주입. 통계 테스트도 시드를 고정해 flaky 하지 않다.
3. **TC 번호로 잇는다.** 모든 자동화 테스트에 `[TC("...")]`. 리포트가 문서와 결과를 자동으로 대조한다.
4. **테스트를 테스트한다.** 뮤테이션 스모크로 대표 버그 15개를 넣어 테스트가 잡는지 확인한다.

## 4. 통계 테스트 기준

- 카이제곱 적합도 검정, 유의수준 0.001 (시드 고정이라 같은 코드면 항상 같은 p값).
- 천장 포함 실제 확률: 이론값 `p / (1 - (1-p)^N)` 과 공시값 비교. 시뮬레이션 관측값은 공시값 ± 4σ + 반올림 오차 이내.
- 확률 검증기는 배너당 100만 회(CI), 단위 테스트는 20~30만 회.

## 5. 결과 판정 (릴리스 기준)

- P0 TC 실패 0, 자동화 누락 0, 문서에 없는 TC 번호 0.
- 데이터 검사 Error 0.
- 확률 검증 전부 통과.
- 미실행(실행 환경 없음)이 있으면 "실행한 범위 통과"로만 표시하고 릴리스 판정은 보류.

## 6. CI 확장 (Unity 테스트)

지금은 Unity 라이선스가 필요 없는 부분만 GitHub Actions에서 돈다. Unity 테스트까지 CI에 올리려면:

1. Unity Personal 라이선스 파일을 저장소 시크릿 `UNITY_LICENSE`, `UNITY_EMAIL`, `UNITY_PASSWORD`로 등록
2. `game-ci/unity-test-runner`로 `testMode: all`, `projectPath: UnityProject` 실행
3. 결과 XML을 `qa report --results ...,unity-editmode=...,unity-playmode=...` 에 함께 넣기

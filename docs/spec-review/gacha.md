# 기획 리뷰 — 모집·천장

> **사후 작성입니다.** 이 프로젝트에는 따로 기획서가 없고 코드와 데이터(`banners.json`)가 곧 기획입니다. 이 문서는 "기획서가 나왔을 때 QA가 리뷰 회의 전에 이런 식으로 정리해 간다"는 형식을, 지금의 코드·데이터를 기획서로 놓고 시연한 것입니다. "결정" 칸은 현재 코드의 동작이며, 실제 프로젝트라면 회의에서 기획자가 정할 자리입니다.

- 대상: 모집(가챠) — 1회/10연 모집, 등급 확률, 천장, 10연 보정, 픽업, 확률 공시
- 기준 코드: `1db01a0` (`Core/Gacha/GachaService.cs`, `Core/GameSession.cs`, `Core/Data/DataValidator.cs`, `Game/GameApp.cs`)
- 기준 데이터: `StreamingAssets/GameData/banners.json`

## 1. 기획 요약 (QA가 이해한 대로 다시 적기)

리뷰는 먼저 "내가 이해한 규칙"을 기획자 확인을 받을 수 있는 문장으로 다시 적는 데서 시작합니다. 여기서 어긋나면 TC가 전부 어긋납니다.

| # | 규칙 | 근거 | TC |
|---|---|---|---|
| R1 | 1회 150 보석, 10연 1,500 보석 (할인 없음) | `CostPerPull: 150`, 10연 = ×10 | GACHA-001, GACHA-003 |
| R2 | 보석이 비용보다 적으면 실패, 같으면 성공 | `State.Gems < cost` | GACHA-002 |
| R3 | 등급 확률 3성 2.5% / 2성 18% / 1성 79.5% | `RateBp` 250/1800/7950 | GACHA-009 |
| R4 | 마지막 3성 이후 90번째 모집은 3성 확정 | `count >= HardPity`, `HardPity: 90` | GACHA-004, GACHA-012 |
| R5 | 3성이 나오면(천장이든 아니든) 천장 카운트 0 | `PullsSinceThreeStar = rarity == 3성 ? 0 : count` | GACHA-005 |
| R6 | 천장 카운트는 배너마다 따로 | `State.Pity[bannerId]` | GACHA-006 |
| R7 | 10연에서 앞 9장이 모두 1성이면 10번째는 2성 이상 | `TenPullGuarantee` | GACHA-007, GACHA-008 |
| R8 | 픽업 배너의 3성은 50% 확률로 픽업, 아니면 나머지 3성 중 균등 | `PickupShareBp: 5000` | GACHA-010 |
| R9 | 천장 포함 실제 3성 확률 2.79%를 공시 | `DisclosedEffectiveThreeStarBp: 279`, 계산식 `p / (1-(1-p)^N)` | DATA-008, GACHA-011 |
| R10 | 같은 캐릭터를 또 뽑으면 보유 수만 늘어남 (다른 재화로 바뀌지 않음) | `Owned[id] = n + 1` | GACHA-013 |
| R11 | 모집이 데이터 오류로 실패하면 보석·천장·보유 그대로 | `DataError` | GACHA-015 |

## 2. 질문과 결정

모호하거나 기획서에 없을 법한 경우를 질문으로 만들고, 답(결정)을 받아 TC로 잇습니다. TC가 없는 항목은 "추가 후보"로 남깁니다.

| # | 질문 | 결정 (현재 동작) | TC | 리스크 |
|---|---|---|---|---|
| Q1 | **천장으로 나온 3성도 픽업 50% 판정을 하나?** 아니면 천장은 픽업 확정인가? | 판정함. 천장 3성도 50%로 픽업/비픽업 | GACHA-010 (3성 전체 비율만 봄) → **천장 3성의 픽업 비율 TC 추가 후보** | 사용자가 "천장 = 픽업 확정"으로 이해할 수 있음. 공시 문구에 명시 필요 |
| Q2 | 픽업을 놓친 다음 3성은 픽업 확정인가? ("반천장") | 아님. 매번 독립 50% | 없음 (현재 규칙에 없어서) | 경쟁 게임과 비교해 문의가 많을 수 있는 부분. 기획 의도 확인 |
| Q3 | **천장 카운트는 배너가 바뀌면 이어지나?** | 배너 id별로 따로 쌓이고, 배너 기간·종료 개념이 없음 | GACHA-006 | 픽업 배너 교체 시 이월/초기화 정책이 없음. 라이브에서 가장 민감한 부분이라 출시 전 결정 필요 |
| Q4 | 10연 도중 천장에 닿으면? (예: 카운트 85에서 10연) | 10장 각각 카운트를 올리고, 90번째 장에서 3성 확정 후 0부터 다시 셈 | GACHA-004는 1회 모집만 봄 → **10연이 천장을 가로지르는 TC 추가 후보** | 10연 안에서 카운트 계산을 따로 구현하면 어긋나기 쉬움 |
| Q5 | 10연 10번째 장이 천장이면 보정과 천장 중 무엇이 적용? | 천장이 먼저. 사유 `HardPity`로 표시 | 없음 → 추가 후보 | 결과 화면 사유 표시("천장")가 맞는지 |
| Q6 | 2성 보정으로 나온 2성도 천장 카운트를 올리나? | 올림 (3성이 아니면 모두 +1) | GACHA-005 간접 | 낮음 |
| Q7 | 홈의 "천장까지 N회"는 무엇을 뜻하나? | `90 - 카운트`. 카운트 89면 "천장까지 1회" = 다음 모집이 확정 | 없음 (UI 표시) → 체크리스트 SMK-06 | "1회 남음"을 "1회 더 뽑은 다음"으로 읽을 수 있음. 문구 확인 |
| Q8 | **2성이 없는 배너(2성 0%)에서 10연 보정은?** | **결정: 10연 보정이 켜진 배너는 2성 후보 필수.** 없으면 데이터 검사기 Error(빌드 전에 막힘). 보정 규칙(2성으로 올림)은 그대로. 검사를 거치지 않고 들어오면 10연이 `DataError`로 실패하고 보석·천장·보유는 그대로 | DATA-010, GACHA-015 | [BUG-002](../bug-reports/BUG-002-ten-pull-guarantee-without-two-star-pool.md)로 실제 결함 확인 후 수정. 3성으로 올림/보정 끄기는 확률 공시가 바뀌어 택하지 않음 |
| Q9 | 공시 확률 2.79%의 반올림은? 계산값과 얼마나 달라도 되나? | 계산값 2.785…%를 소수 둘째 자리로 반올림. 검사기는 ±1bp(0.01%p)까지 허용 | DATA-008 | 공시 규정이 요구하는 자릿수와 맞는지 확인 |
| Q10 | 실제 확률 검증은 얼마나 돌리고, 얼마나 벗어나면 실패인가? | 배너당 100만 회, 공시값 ± 4σ + 반올림 오차 | GACHA-011, `qa gacha-verify` | 장기 평균만 보면 천장 off-by-one을 놓침 → 최대 간격도 함께 봄 ([DEMO-001](../bug-reports/DEMO-001-pity-off-by-one.md)) |
| Q11 | 다음 모집 결과를 정하는 시드가 세이브에 저장되는데, 세이브를 복사해 두고 결과를 미리 볼 수 있지 않나? | 가능. 오프라인 게임이라 세이브-로드 후 같은 결과가 나오게 한 의도된 설계 | SAVE-005 | 온라인 전환 시 모집은 서버 추첨으로 옮겨야 함. 지금 범위 밖(TEST_PLAN 1장)이지만 기록 |
| Q12 | 1회·10회 외(예: 5회) 모집은? | 허용 안 함 (예외) | GACHA-014 | 낮음 |
| Q13 | 3성 기본 확률이 0%인 배너는? | 천장이 있으면 실제 확률 = 1/90 (약 1.11%)로 계산 | 없음 | 이벤트 배너 설계 시 공시값 계산 확인 |

## 3. 리스크 정리

| 리스크 | 영향 | 대응 | 상태 |
|---|---|---|---|
| 공시 확률과 실제 동작 불일치 | 법적·신뢰 문제 | 통계 검정 + 천장 간격 + 경계값 TC, CI에서 배너당 100만 회 | 대응됨 |
| 실패한 모집이 재화만 가져감 | 재화 손실, CS | 원자적 반영 + GACHA-015 | 대응됨 ([BUG-001](../bug-reports/BUG-001-gems-taken-on-failed-pull.md)) |
| 데이터 검사기가 보정용 후보 누락을 못 잡음 | 특정 배너 10연 불가 | DATA-010 + 검사 규칙 추가 | 대응됨 ([BUG-002](../bug-reports/BUG-002-ten-pull-guarantee-without-two-star-pool.md)) |
| 배너 교체 시 천장 이월 정책 없음 | 라이브 운영 혼란 | 기획 결정 필요 (Q3) | 열림 |
| 천장 3성의 픽업 여부 안내 부족 | 문의·불만 | 공시 문구 확인 (Q1) | 열림 |

## 이 리뷰를 어떻게 했나

1. 코드·데이터에서 규칙을 문장으로 뽑아 1장 표를 만들고, 규칙마다 TC가 있는지 대조했습니다.
2. 규칙끼리 만나는 지점(천장×10연, 천장×픽업, 보정×데이터)을 질문으로 만들었습니다. 결함은 대부분 규칙 하나가 아니라 **규칙 두 개가 겹치는 곳**에서 나옵니다.
3. 의심 가는 질문은 코드로 직접 돌려 봤습니다. Q8은 그렇게 해서 실제 결함(BUG-002)으로 확인됐고, 검사기 규칙과 회귀 TC(DATA-010)로 고쳤습니다.
